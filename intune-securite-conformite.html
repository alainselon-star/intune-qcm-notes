Microsoft Intune — Sécurité et conformité des appareils

Fiche de synthèse du chapitre « Sécurité et conformité » — un seul fil conducteur du général au particulier

La menace n'entre presque jamais par le réseau : ce sont les postes, les serveurs et désormais les mobiles qui la propagent. La question posée par ce chapitre est donc simple à énoncer et difficile à tenir : comment s'assurer qu'aucun appareil accédant aux ressources de l'organisation, quel que soit son système d'exploitation, ne devienne une porte d'entrée pour un attaquant ou un canal de fuite de données — sans bloquer l'activité des utilisateurs ? Tous les mécanismes de ce chapitre, du firewall Windows aux stratégies de conformité Android, répondent en réalité à une seule et même logique en trois temps.

1.Le fil conducteur

PROTÉGER→ VÉRIFIER→ CONTRÔLER

Protéger Sécurité

Réduire la surface d'attaque de l'appareil et détecter/neutraliser les menaces : antivirus, firewall, chiffrement, navigation sécurisée, durcissement, gestion des privilèges et de l'identité.

Vérifier Conformité

Mesurer si l'état réel de l'appareil correspond à l'état attendu, défini dans un référentiel. C'est le rôle des stratégies de conformité Intune.

Contrôler Accès conditionnel

Conditionner l'accès aux ressources de l'organisation au résultat des deux étages précédents, via Microsoft Entra ID.

Ce triptyque se retrouve à l'identique que l'appareil soit un ordinateur ou un mobile, qu'il soit géré de façon traditionnelle (Active Directory, Configuration Manager) ou moderne (Intune, Defender for Endpoint). Seuls les outils changent, jamais la logique — c'est le repère à retenir pour reconstituer tout le chapitre.

2.Sécurité et conformité : deux notions à distinguer

Sécurité L'objectif

L'ensemble des mesures techniques et organisationnelles, préventives et réactives, qui protègent la confidentialité, l'intégrité et la disponibilité (DIC) des systèmes et des données. Un antivirus, un firewall, un chiffrement de disque agissent directement sur le risque.

Conformité La mesure

La vérification qu'un état observé (la configuration réelle d'un appareil) correspond à un état attendu, défini dans un référentiel interne ou réglementaire. La conformité ne protège rien par elle-même ; elle constate un écart, ou son absence.

Le point commun : nécessaire, mais non suffisant Un appareil conforme à l'instant T peut être compromis l'instant d'après par une menace que le référentiel ne testait pas. La conformité doit donc être couplée à une solution de détection continue comme Microsoft Defender for Endpoint (MDE) — dont le niveau de risque peut lui-même devenir un critère de conformité. Les deux mécanismes se nourrissent l'un l'autre : c'est cette articulation qui structure tout le chapitre.

3.Deux modes de gestion

ModePrincipeCas typique
TraditionnelAppareil joint à Active Directory, piloté par stratégies de groupe, ou géré par Microsoft Configuration Manager.Parc historique, postes non cloud-natifs
ModerneAppareil enregistré et géré par Microsoft Intune, ou seulement intégré à Microsoft Defender for Endpoint sans être géré par Intune.Postes cloud-natifs ; serveurs, filiales, postes non gérés côté MDE

C'est la seconde voie qui est détaillée dans ce chapitre. Trois prérequis pour piloter la sécurité via MDE seul : accès au point de terminaison *.dm.microsoft.com, version d'OS supportée, licence adaptée (Defender for Endpoint Plan 1/2/Business, ou Defender for Servers). Le connecteur MDE/Intune (portail Defender → System - Settings - Endpoints → Microsoft Intune Connection) partage ensuite les signaux de risque utilisés à l'étage Vérifier.

Repère de configuration : en 2023, Microsoft a migré les stratégies héritées vers le settings catalog. Trois voies coexistent : une stratégie settings catalog (paramètres précis), une stratégie Endpoint Security (regroupe un thème de sécurité complet — la voie retenue ici), ou une Security Baseline (socle transverse de valeurs recommandées).

4.Étage Protéger — ordinateurs et serveurs Protéger

Chaque brique répond à un « pourquoi » précis, rattaché à la confidentialité, l'intégrité ou la disponibilité :

Antivirus / EDR Réactif

Microsoft Defender : configuration, mise à jour des définitions, traitement des menaces détectées.

Firewall Préventif

Bloque les intrusions entrantes et contient les communications sortantes d'une machine déjà compromise.

Chiffrement du stockage

Protège la confidentialité des données au repos en cas de perte ou de vol (BitLocker, FileVault).

Navigation sécurisée

Ferme un vecteur d'entrée majeur : liens ouverts par l'utilisateur, sites malveillants (SmartScreen, Network Protection).

Durcissement / lignes de base

Réduit la surface d'attaque par défaut en imposant un socle de configuration.

Privilèges et identité

Limite les mouvements latéraux — la technique la plus utilisée par un attaquant une fois entré dans l'organisation.

Ces briques se configurent via le nœud Endpoint Security, qui regroupe tous les paramétrages d'un même thème de sécurité.

5.Étage Protéger — cas particulier : mobiles Protéger

Même triptyque, seule la surface d'attaque change. Les plateformes mobiles sont globalement bien sécurisées tant que le terminal n'a pas été modifié via le jailbreak (iOS/iPadOS) ou le rootage (Android) — l'étage Vérifier détecte ces dérives. Référentiels complémentaires : CIS (downloads.cisecurity.org) et NIST SP 800-124r2.

PlateformeModes supportés par MDENon supportés
AndroidEnterprise (Work Profile, Fully Managed, COBO, COPE), Device AdministratorDedicated (COSU/Kiosk), AOSP
iOS/iPadOSSupervisé (ADE, Apple Configurator), non supervisé (Device/User Enrollment), MAMDedicated/Shared/Kiosk

Déploiement : Android via Managed Google Play Store + stratégie Restriction (VPN) ; iOS/iPadOS via Apple Business Manager + profil Custom ou VPN. En mode MAM, le paramètre Max allowed device threat level ajouté aux conditions de lancement de la stratégie de protection d'application relie directement le risque MDE (Protéger) à l'accès à l'application.

6.Étage Vérifier — conformité des appareils Vérifier

Vérifier consiste à définir un référentiel (une stratégie de conformité), l'évaluer sur chaque appareil, et signaler l'écart.

Paramètres généraux

Appareil sans stratégie assignée : non conforme par défaut recommandé. Intervalle de remontée d'état : 30 jours par défaut (1 à 120 jours) ; au-delà, appareil silencieux = non conforme.

Actions en cas de non-conformité

E-mail à l'utilisateur, notification poussée (iOS/iPadOS, Android Enterprise), verrouillage à distance, ajout à la liste de mise hors service (validation manuelle requise). Scénario progressif possible : grâce → non-conforme → retrait.

Déclinaison par plateforme

PlateformePoints clés vérifiés
WindowsBitLocker au démarrage, Secure Boot, intégrité de code (via Attestation Service) ; version d'OS min/max ; conformité Configuration Manager ; mot de passe, firewall/TPM/antivirus ; niveau de risque MDE (Clear/Low/Medium/High — non intégré à MDE = non conforme) ; distributions WSL autorisées.
macOSProtection d'intégrité du système (SIP) ; version/build min/max ; mot de passe ; firewall (Stealth) ; System Policy Control (ex-Gatekeeper).
LinuxDistributions/versions autorisées ; chiffrement du stockage ; complexité du mot de passe ; conformité personnalisée (script + JSON).
iOS/iPadOSCompte mail préexistant → non conforme ; blocage jailbreak ; version/build Apple ; niveau de risque MDE ; applications restreintes (bundle-id).
AndroidEnterprise (Work Profile/Fully Managed/COPE) : niveau de risque MDE, blocage root, Google Play Protect, patch de sécurité, mot de passe appareil + profil pro. AOSP : blocage root, version/patch, mot de passe.

Scripts de conformité personnalisée

Windows et Linux seulement : un script de découverte renvoie un résultat JSON, validé par un fichier de règles (SettingName, Operator, DataType, Operand, MoreInfoURL, RemediationStrings). Limite : 100 Ko et 100 règles par fichier.

$hash = @{ Manufacturer = $WMI_ComputerSystem.Manufacturer; BiosVersion = $WMI_BIOS.SMBIOSBIOSVersion; TPMChipPresent = $TPM.TPMPresent } return $hash | ConvertTo-Json -Compress
{ "SettingName":"BiosVersion", "Operator":"GreaterEquals", "DataType":"Version", "Operand":"2.3" }

Import : Endpoint Security → Manage → Device Compliance → Scripts. Une fois importé, le script s'utilise dans une stratégie de conformité, couplé au fichier JSON.

7.Étage Contrôler — accès conditionnel Contrôler

Cet étage combine les deux précédents : le signal de risque de Protéger (MDE) et le résultat de Vérifier (conformité Intune) deviennent des conditions d'accès, dans la logique Zero Trust de Microsoft Entra ID.

Conditions

Risque utilisateur, risque de connexion, risque interne, plateforme, application cliente, flux d'authentification, filtres sur l'appareil.

Contrôles d'accès

Identité (MFA, authentification forte) ; appareil conforme via Intune ou joint hybride ; application protégée par une stratégie MAM.

Contrôles de session

Restrictions d'applications forcées, Defender for Cloud Apps, fréquence de connexion, évaluation d'accès continue (CAE), protection de jeton, Global Secure Access.
