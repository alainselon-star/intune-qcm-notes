Labo Intune — Droits et permissions (RBAC)

Mise en pratique du chapitre « Gestion des droits et des permissions » sur un tenant réel

Scénario : vous mettez en place une délégation Helpdesk limitée aux postes Windows d'un site fictif « Paris », sans droit sur les serveurs ni les autres sites — le cas d'usage RACI que le chapitre appelle de ses vœux. Chaque exercice ci-dessous reprend une section précise de la fiche de cours et se termine par une vérification concrète, sans avoir besoin de vous reconnecter avec le compte test.

Prérequis à vérifier avant de commencer Licence Intune sur votre compte admin (Business Premium suffit pour les exercices 1 à 6). L'exercice 7 (PIM) exige Entra ID P2 ou Entra ID Governance — vérifiez dans Entra ID → Licenses. L'exercice 8 (Multi-Admin Approval) fait partie d'Intune Suite — s'il est grisé, traitez-le en observation plutôt qu'en exécution. Tenant utilisé : NextstepPRO.onmicrosoft.com (ou votre tenant de pratique).
Cours § 1 — RBAC : le modèle et ses trois briques

Exercice 1 — Créer les deux groupes de base Qui

But : matérialiser concrètement les deux rôles que joue un groupe de sécurité dans le modèle — porteur de droits (le groupe d'admins) et cible de ces droits (le groupe de ressources).
  1. Entra ID → Groups → New groupType : Security. Nom : SG-Helpdesk-Paris. Description : « Administrateurs Helpdesk périmètre Paris ».
  2. Entra ID → Users → New userNom d'affichage : Test Helpdesk 1. Identifiant : test.helpdesk1@NextstepPRO.onmicrosoft.com. Pas de licence M365 nécessaire à ce stade.
  3. Ajouter le membreRetournez sur SG-Helpdesk-Paris → Members → Add members → test.helpdesk1.
  4. Créer le second groupeNew group → Security → Nom : SG-Devices-Paris → Description : « Postes Windows du site Paris ». Membres assignés vides pour l'instant (on y reviendra à l'exercice 5 si vous avez un appareil de test).
Résultat attenduDeux groupes visibles dans Entra ID → Groups, SG-Helpdesk-Paris contenant un membre (test.helpdesk1), SG-Devices-Paris vide ou avec un appareil de test.
Cours § 2 — Rôles : deux niveaux

Exercice 2 — Lire un rôle intégré, puis en cloner un Quelles actions

But : comprendre la granularité réelle d'un rôle Intune (classes d'objets × permissions) avant d'en construire un sur mesure.
  1. Intune → Tenant administration → Roles → All rolesOuvrez Help Desk Operator → onglet Manage → Permissions. Repérez au moins 3 classes d'objets (ex. Managed devices, Remote tasks, Managed apps) et notez ce qui est coché (Read/Update/Delete…).
  2. Créer un rôle personnaliséAll roles → Create → Intune Role. Nom : Helpdesk-Paris-Limite. Description : « Helpdesk Paris, sans verrouillage/effacement à distance ».
  3. Copier les permissionsDans l'assistant, section Permissions : reproduisez celles de Help Desk Operator pour Managed devices et Remote tasks, mais décochez explicitement Remote lock et Wipe.
  4. Balise d'étendue par défautLaissez « Default » à cette étape (l'exercice 3 en créera une dédiée).
Résultat attenduHelpdesk-Paris-Limite apparaît dans All roles avec la mention « Custom ». Comparez son résumé de permissions à celui de Help Desk Operator : la différence doit se limiter à Remote lock/Wipe.

Rappel du cours : les rôles intégrés ne se modifient pas — c'est pour ça qu'on clone plutôt que d'éditer Help Desk Operator directement.

Cours § 3 — Balises d'étendue (scope tags)

Exercice 3 — Créer et assigner une balise Sur quoi

But : délimiter visuellement et fonctionnellement le périmètre « Paris » avant de l'utiliser dans l'assignment.
  1. Tenant administration → Roles → Scope tags → CreateNom : Paris. Description : « Objets rattachés au site Paris ».
  2. Assignation à un groupeÀ l'étape Assign de l'assistant, sélectionnez SG-Devices-Paris — la balise s'appliquera à ce groupe et aux appareils qui lui sont associés.
  3. ValiderLa balise Paris doit apparaître dans la liste Scope tags avec 1 assignment.
Résultat attenduLa balise Paris existe et est assignée à SG-Devices-Paris. Elle n'est pas encore appliquée à un objet précis (stratégie, appli…) — c'est normal, ça se fait objet par objet à la création.
Cours § 4 — Assigner des droits

Exercice 4 — Assembler les trois briques Droit réel

But : produire le « droit réel » du modèle — l'assignment est le seul endroit où groupe, rôle et balise se rencontrent effectivement.
  1. All roles → Helpdesk-Paris-Limite → Manage → Assignments → AssignNom de l'assignment : Helpdesk-Paris.
  2. Groupe des administrateursSG-Helpdesk-Paris — qui reçoit ce rôle.
  3. Groupe(s) cible(s)SG-Devices-Paris — sur quoi ces administrateurs peuvent intervenir.
  4. Balise(s) d'étendueParis plutôt que Default — c'est ce qui garantit que même si le groupe cible s'élargit un jour, seuls les objets tagués Paris resteront visibles.
  5. ValiderVérifiez le résumé avant de confirmer : rôle, groupe admin, groupe cible et balise doivent tous les quatre apparaître.
Résultat attendu — vérification sans reconnexionIntune → Troubleshooting + support → recherchez test.helpdesk1 → onglet Assigned roles : Helpdesk-Paris-Limite doit apparaître, scopé à Paris.
Cours § 1 (note licence)

Exercice 5 — Dispenser le compte test de licence Intune

But : vérifier concrètement le mécanisme d'exemption mentionné en note du chapitre, pour ne pas consommer une licence sur un compte purement administratif.
  1. Tenant administration → Roles → Administrator LicensingAjoutez test.helpdesk1 à la liste des comptes exemptés.
Résultat attendutest.helpdesk1 garde l'accès au centre d'administration Intune sans qu'une licence Intune/M365 lui soit assignée.
Cours § 5 — Unités d'administration

Exercice 6 — Créer une unité d'administration et comparer au scope tag Structurel

But : expérimenter la différence entre les deux mécanismes de découpage — la balise d'étendue scope des objets Intune, l'unité d'administration scope l'annuaire Entra ID (utilisateurs, mots de passe, authentification).
  1. Entra ID → Roles & admins → Administrative units → NewNom : AU-Paris.
  2. Ajouter des membresOnglet Groups → Add → SG-Devices-Paris (si votre tenant permet d'y ajouter des groupes de périphériques ; sinon ajoutez test.helpdesk1 comme utilisateur membre pour l'exercice).
  3. Assigner un rôle scopé à l'unitéOnglet Roles and administrators → Add assignments → un rôle éligible (ex. Helpdesk Administrator, Password Administrator) → SG-Helpdesk-Paris.
Résultat attenduAU-Paris existe avec ses membres et un rôle Entra scopé. Notez que ce rôle Entra ne vous a rien donné sur les objets Intune — c'est un mécanisme parallèle au RBAC Intune, pas un remplacement.
Cours § 6 — Privileged Identity Management (PIM)

Exercice 7 — Rendre un accès éligible plutôt que permanent Just-in-Time

But : transformer un droit permanent (Active) en droit à la demande (Eligible), la dimension « temps » qu'introduit PIM.
Licence requiseEntra ID P2 ou Entra ID Governance. Si Identity Governance → PIM n'apparaît pas ou renvoie une erreur de licence, passez cet exercice et notez-le « à refaire » dans votre carnet de suivi.
  1. Identity Governance → Privileged Identity Management → Manage → GroupsDiscover groups → sélectionnez SG-Helpdesk-Paris (le groupe porteur du rôle Intune) → Manage groups.
  2. Assignments → Add assignmentsRôle Member → utilisateur test.helpdesk1 (ou un groupe).
  3. Type d'assignationChoisissez Eligible, durée maximale 8 heures.
  4. Settings → Member roleActivez « Require justification on activation » et « Require approval » avec un approbateur désigné.
Résultat attendutest.helpdesk1 n'a plus d'accès permanent au groupe (donc au rôle Helpdesk-Paris-Limite) : il devrait devoir en faire la demande via My Access / PIM avant que le droit ne s'active, pour une durée limitée.
Cours § 7 — Approbation multi-admin (MAA)

Exercice 8 — Observer (ou mettre en place) une double validation Collaboratif

But : comprendre le cycle demande → approbation → exécution, même si votre licence ne permet pas d'aller jusqu'au bout.
  1. Tenant administration → Multi Admin Approval → Access Policy → CreateSi le menu est grisé ou absent : c'est qu'Intune Suite n'est pas dans votre licence — documentez le principe ci-dessous sans exécuter.
  2. Nom, description, type de profilEx. MAA-Scripts-Critiques, type de profil : Script.
  3. Plateformes concernéesWindows uniquement, pour cet exercice.
  4. Groupe d'approbateursSG-Helpdesk-Paris ne devrait pas être approbateur de ses propres actions — créez plutôt un groupe distinct SG-Approbateurs-Securite si vous allez au bout.
  5. Soumission pour approbationLa politique elle-même doit être validée par un autre administrateur avant de devenir active — notez cette exigence même si vous ne pouvez pas la tester matériellement.
Résultat attenduSoit une politique MAA active et en attente de validation, soit — si la fonctionnalité n'est pas disponible — une note claire dans votre carnet expliquant le cycle en 3 temps (demande/approbation/exécution) et pourquoi une seule personne ne doit jamais être à la fois demandeur et approbateur.
