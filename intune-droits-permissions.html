Microsoft Intune — Gestion des droits et des permissions

Fiche de synthèse du chapitre « Gestion des droits et des permissions »

Ce chapitre répond à une question précise : une fois un appareil géré par Intune, qui a le droit de faire quoi, sur quoi, et pendant combien de temps ? Il pose d'abord le modèle RBAC et ses trois briques (rôle, balise d'étendue, groupe), détaille chaque brique, puis montre comment les assembler. Deux mécanismes complémentaires viennent ensuite renforcer ce socle : les unités d'administration (découpage structurel), puis PIM et l'approbation multi-admin, qui ajoutent respectivement une dimension temporelle et une validation collaborative.

Le cas d'école qui justifie le chapitre En juillet 2012, une banque australienne a été paralysée par l'application, sur les postes de travail, d'une mise à jour insuffisamment testée — déployée par un technicien qui n'aurait pas dû pouvoir cibler ces ressources. Microsoft Configuration Manager (l'ancêtre d'Intune) donne un accès complet aux ressources administrées : sans planification de la sécurité des droits, un outil de gestion devient un outil de destruction potentiel.

1.RBAC : le modèle et ses trois briques

Le contrôle d'accès basé sur les rôles (Role-Based Access Control) a été proposé par Ferraiolo et Kuhn en 1992, validé par le NIST en 2004. Microsoft l'a introduit dès Windows XP / Server 2003 SP1 (API Authorization Manager), puis complété avec Exchange Server 2010. Le modèle Role-Based Administration de Microsoft Intune s'appuie sur trois briques :

Groupe de sécurité
qui + Rôle de sécurité
quelles actions + Balise d'étendue
sur quoi = Assignment
droit réel

Groupes Qui

Les utilisateurs administratifs sont rassemblés dans un groupe de sécurité Microsoft Entra ID, qui obtient les permissions pour agir. La manipulation des groupes eux-mêmes (création, appartenance) reste régie par le RBAC natif d'Entra ID — les deux modèles se couplent selon les responsabilités.

Rôles de sécurité Quelles actions

Définissent un ensemble de permissions relatives à un périmètre de responsabilités et d'actions (lecture, modification, suppression, création, assignation, rapport, contrôle distant…).

Balises d'étendue (scope tags) Sur quoi

Définissent quels objets (stratégies, profils, applications…) un administrateur peut voir. Associées au groupe et au rôle, elles délimitent le périmètre d'intervention.

Point de licence : les administrateurs doivent théoriquement disposer d'une licence Intune pour accéder au centre d'administration. L'option Tenant administration → Roles → Administrator Licensing permet d'en dispenser les comptes purement administratifs.

Rôles prédéfinis vs rôles personnalisés Les permissions des rôles intégrés ne peuvent pas être modifiées. Créer un rôle personnalisé impose de la gestion de changement : Microsoft n'ajoute pas automatiquement les nouvelles classes aux rôles créés soi-même. Recommandation générale : privilégier les rôles au niveau Intune pour appliquer le principe de moindre privilège du Zero Trust ; réserver le custom aux besoins que les rôles prédéfinis ne couvrent pas.

Créer un rôle personnalisé

  1. Tenant administration → Roles → All rolesCliquer sur Create, puis Intune Role, Windows 365 Role ou Windows Autopatch role.
  2. Nom et descriptionIdentification du rôle.
  3. Classes et permissionsSélection des classes d'objets et des permissions associées.
  4. Balise d'étendueConfiguration d'une balise d'étendue par défaut pour le rôle.
  5. ValidationCréation du rôle.

3.Balises d'étendue (scope tags)

Elles définissent les objets (stratégies, tokens, applications…) que les administrateurs peuvent voir. Cas d'usage typiques : découpage par équipe (postes / mobiles / serveurs), par géographie (France, États-Unis…), ou par état d'approbation d'un objet (une application en cours de packaging porte une balise « équipe test », puis change de balise une fois prête pour l'équipe déploiement). Une balise par défaut s'applique automatiquement à tout objet non marqué qui prend en charge ce mécanisme.

  1. Tenant administration → Roles → Scope tagsCliquer sur Create.
  2. Nom et descriptionIdentification de la balise.
  3. Assignation à un groupeLa balise s'applique au groupe et à tous les périphériques associés.
  4. ValidationCréation de la balise.

L'assignation effective d'une balise se fait ensuite lors de la création de chaque objet (stratégie, application…) qui supporte ce mécanisme.

4.Assigner des droits

Une fois rôles, balises d'étendue et groupes créés, l'assemblage se fait via Tenant administration → Roles → All Roles, en sélectionnant le rôle puis Manage → Assignments → Assign :

  1. Nom et description de l'assignationIdentification de l'assignation.
  2. Groupe des administrateursQui reçoit ce rôle.
  3. Groupe(s) cible(s)Utilisateurs et/ou périphériques sur lesquels ces administrateurs peuvent intervenir — possibilité de cibler tous les utilisateurs/périphériques.
  4. Balise(s) d'étendueBalise par défaut (accès à tous les objets) ou balise personnalisée selon le modèle de délégation.
  5. ValidationRésumé puis assignation. À répéter pour construire le modèle complet, aligné sur la matrice RACI de l'organisation.

5.Unités d'administration

Les unités d'administration (admin units) créent des divisions logiques dans l'annuaire — départements, régions, équipes projet — particulièrement utiles dans les grandes entreprises. Chaque unité peut avoir ses propres administrateurs, avec une gestion plus ciblée : par exemple, un responsable local de pays peut gérer les accès de son périmètre sans validation centralisée. Une unité d'administration comprend :

  • Ses propriétés (membres assignés ou calculés dynamiquement, sur base d'utilisateurs ou de périphériques)
  • Les utilisateurs membres
  • Les groupes membres associés
  • Les périphériques associés
  • Les rôles et administrateurs à droits périmétrés à cette unité (tous les rôles Entra ne sont pas éligibles — surtout des rôles de gestion quotidienne : groupes, utilisateurs, périphériques, mots de passe, authentification)

Mécanisme complémentaire au RBAC Intune, plutôt qu'un remplacement — pertinent quand rôles et responsabilités sont déjà bien établis dans l'organisation.

6.Privileged Identity Management (PIM)

Service Entra ID qui ajoute la dimension temps au modèle : accès juste-à-temps (Just-in-Time) aux opérations critiques plutôt qu'un droit permanent. Couvre Entra ID, Azure et Intune. Licence requise : Entra ID P2 ou Entra ID Governance. Utilisable sur les rôles Entra ID, mais aussi sur des groupes de sécurité cloud porteurs d'un rôle Intune.

Eligible Bonne pratique

L'utilisateur peut demander les droits, mais ne les a pas d'office — il doit les activer.

Active Droit permanent

L'utilisateur a les droits dès sa connexion au portail.

Attribution permanente ou limitée dans le temps (date de début/fin, maximum un an).

Mise en œuvre — rôles Microsoft Entra

  1. Identity Governance → Privileged Identity Management → Manage → Microsoft Entra RolesSélectionner le rôle cible, ex. Intune Administrator.
  2. Assignments → Add assignmentsAssocier des utilisateurs directement, ou via un groupe Microsoft 365.
  3. Type d'assignationEligible ou Active, avec durée permanente ou limitée.

Mise en œuvre — groupes porteurs d'un rôle Intune

  1. Groups → Discover GroupsSélectionner le groupe auquel un rôle Intune a été assigné, puis Manage groups.
  2. Assignments → Add assignmentsAssocier des utilisateurs directement ou via un groupe de sécurité ; sélectionner le rôle Member.
  3. Type d'assignationEligible ou Active, comme pour les rôles Entra.

L'espace Settings (rôles ou groupes) permet de configurer les paramètres d'activation (justification, approbateurs, durée), d'assignation (expiration de l'éligibilité) et de notifications.

7.Approbation multi-admin (MAA)

Le Multi Admin Approval ajoute une couche de validation collaborative : les actions critiques spécifiques doivent recevoir l'aval de plusieurs administrateurs avant exécution, réduisant le risque lié à un compte administrateur compromis agissant seul.

Mise en place : définir qui peut créer/approuver les politiques MAA, formaliser une politique d'accès (matrice RACI) listant les actions concernées, puis faire vivre le cycle demande → approbation → exécution.

  1. Tenant administration → Multi Admin Approval → Access Policy → CreateLa vue liste aussi toutes les demandes et celles de l'utilisateur connecté.
  2. Nom, description, type de profilEx. Script, Applications.
  3. Plateformes concernéesWindows uniquement, et/ou plateformes non Windows.
  4. Groupe d'approbateursUtilisateurs habilités à approuver les actions.
  5. Soumission pour approbationLa stratégie d'accès elle-même doit être validée par un autre administrateur avant d'être active.

8.Grille de lecture transverse

MécanismeRépond àType de contrôle

Retenir en une phrase : le RBAC pose le socle statique (rôle + balise d'étendue + groupe) ; les unités d'administration offrent un découpage structurel alternatif ; PIM et l'approbation multi-admin ne remplacent rien, ils ajoutent respectivement une couche temporelle et une couche de validation humaine par-dessus ce socle.
